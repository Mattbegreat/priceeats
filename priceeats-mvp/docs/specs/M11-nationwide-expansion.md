# M11 全台擴張（Matt 11/17 同意方向：先雙北捷運站周邊、願意付費、照片辨識完就刪）

目標：菜單涵蓋全台。作法是「跟著使用者一圈一圈擴」，不是平均鋪。本檔給執行模型（Sonnet／Haiku／agy）照做；規格要改才找 Opus。

- 菜單照片平均每家約 1.9 MB（5.8 GB／3,070 家）。11/17 已刪除已辨識店家的照片 5.1 GB，保留 5% 樣本（店號 % 20 == 0，136 家）與所有 metadata.json。

## M11.0 前置量測（Sonnet，不改程式）
1. Supabase 用量：各表列數（PostgREST count=exact）與資料庫大小（請 Matt 在 Supabase 後台 Database → Usage 讀數字，或用已登入的瀏覽器讀取）；到 Supabase 官方定價頁查目前免費方案上限，附網址與查詢日期。算出「每 1,000 家店約占多少」與「免費額度可撐到幾家」。數字用程式算，不估。
2. OCR 單位時間：從 data/ocr-run.log 算每家平均秒數與每日實際完成數。
3. 產出 docs/specs/M11-capacity.md。

## M11.1 流程改造：串流＋自動刪照片（Sonnet）
新增 scripts/pipeline.sh <area>，把既有腳本串成可續跑的批次：
1. discover_shops.py --area → 2. download_menus.py（每批 50 家）→ 3. run_ocr.sh → 4. build_from_ocr.py → 5. qa_check.py → 6. import（見下）→ 7. 刪除本批已匯入店家的照片（保留店號 % 20 == 0 的樣本與 metadata.json）→ 8. 寫 data/pipeline-state.json（區域、批次、各步完成數、時間）。
- 可續跑：每步完成才記狀態；重跑從未完成的步驟接續；重複執行不重複下載、不重複匯入。
- 磁碟保護：每批開始前檢查可用空間，< 3 GB 就停並記錄。
- 匯入：npm run import:menu 需 SUPABASE_SERVICE_ROLE_KEY（只在 Mac 的 .env.local，不得印出、不得進 repo）。匯入後重跑 npm run gen:area-stats。
- 排程：提供 launchd plist 範本（每晚 01:00，caffeinate -i），由 Matt 自己載入；不要替他改系統設定。
- 前提：Chrome 需以 --remote-debugging-port=9222 開著且已登入 Google；沒開就停並記錄，不嘗試登入。
- 停止條件（任何一項出現就整個停，記錄後回報，不重試、不繞過）：Google 出現驗證碼、異常流量頁、帳號警告；429 額度用完；同一錯誤 3 次。
- 驗收：用一個小區域（例：台北車站，20 家）完整跑一輪，磁碟占用跑完後回到跑之前 ±100 MB；中途中斷再跑可接續；測試全過。

## M11.2 區域清單（agy 整理、Sonnet 驗證）
- agy：從政府開放資料（TDX 或台北捷運、新北捷運公開的車站座標）整理車站清單：站名、路線、緯度、經度、資料來源網址。不確定的寫「待確認」，不可編造座標。
- Sonnet：寫入 data/areas.json（新增欄位 tier、line、source），用程式檢查：座標落在台灣範圍、同站不重複、與既有 8 區中心距離。每站查詢檔沿用 data/queries/area-*.txt 的 30 組樣板自動產生。
- 驗收：scripts/coverage.py 能列出所有區域的店數與進度。

## 每區上線前的品質閘門（Sonnet＋agy）
- 500m 內 ≥ 30 家店；舊資料比例 < 30%；小菜誤判抽查（前 20 道 ≤ 2 筆）。
- OCR 抽樣：從保留的 5% 樣本取 20 家，agy 對照原圖逐項比對價格，錯誤率 > 5% 就不上線並回報。
- 通過才把該區加入前端清單；結果寫入 docs/specs/acceptance-<日期>.md。

## 不能碰
- 不繞過任何驗證碼或流量限制；不使用多個 Google 帳號分散抓取。
- 金鑰不進 repo、不貼在對話。
- 不刪 metadata.json、ocr-raw、menus-maps2。
